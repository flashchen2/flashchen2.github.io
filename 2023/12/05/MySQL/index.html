4. 分组 - group by *

  1. 查询方法：select 字段列表 from 表名 [where 条件] group by 分组字段名[having 分组后过滤条件];

    1. 执行时机不同：where是分组之前进行过滤，不满足where条件的，不参与分组；而having是分组之后对结果进行过滤

  3. 注意：
    1. 执行顺序：where > 聚合函数 > having
    2. 分组之后，查询的字段一般为聚合函数和分组函数，查询其他字段无任何意义

10.distinct 与 order by 的区别

  • 输出结果：两者都会返回列 a 和 b 的唯一组合
  • 主要区别：
    • GROUP BY a, b 通常是为后续聚合函数做准备
    • DISTINCT a, b 明确表示只需要去除重复的行组合
  • 适用场景：
    • 单纯去重 → DISTINCT
    • 需要计算计数、求和等聚合操作 → GROUP BY

四、sql慢查

一般慢查发生时，尝伴随耗时高、主从延迟高的告警

1.常规优化手段

1.优化sql

1.明确查询列

避免使用select *作为查询的列表字段，需要那些字段必须明确写明

2.小表join驱动大表

用数据量较小、索引比较完备的小表，使用其索引和条件，对大表进行数据筛选。从而减少数据计算量，提高查询效率

如：student表有30条数据，score表有80w条数据

3.连接查询代替子查询

如：student表有30条数据，score表有80w条数据，想要查看学号小于15的学员各科分数信息

  • 子查询：需要执行两次数据库查询，一次是外部查询，一次是嵌套子查询
  • 连接查询：可以减少数据库查询的次数，提高查询效率

4.批量操作

批量插入或删除数据，较少频繁的IO操作

5.使用limit

避免过度提取数据，简化查询结果

2.大表拆分

1.水平拆分

  1. 解决单表数据量过大问题，核心规则是范围 / 哈希 / 地理 / 时间，哈希拆分数据分布最均匀
  2. 注意：分库分表过程中，分片键选择（避免数据倾斜）

2.纵向拆分

  1. 解决业务耦合和高频字段查询效率问题，核心按业务模块 / 访问频率拆分。可分割为主表、从表，或两个完全独立的库

3.添加索引

[!NOTE]

【底层原理】增加索引字段，全表扫描->B+树快速查找。有序的排列索引的内容，将相同的数据排在一起，故提高group by的查询效率

  1. 普通索引（单列）
  1. 联合索引（多列）

注：若已创建联合索引 (A, B)，无需再创建普通索引 (A)（联合索引已包含 A 的索引能力）；

  1. 性能对比
    1. 假设有 100 万行数据，查询 WHERE name = ‘张三’ AND age = 25，用两个普通索引（idx_name + idx_age）
    2. 不加索引：数据库需要逐行读取 100 万行数据，对比每行的 name和age，耗时5s
    3. 普通索引：先查 idx_name = “张三” 的主键 ID，再查 idx_age =25 的 ID，最后合并结果，耗时约 50ms
    4. 联合索引（idx_name_age）：直接定位 “张三 + 25” 的主键 ID，耗时约 5ms

2.深翻页问题

1.介绍

  1. 在分页查询中，访问「页码非常靠后」的数据（比如第 1000 页）

  2. 浅分页：查询第 1 页数据（pageNum=1，pageSize=10）

  3. 深分页：查询第 1000 页数据（pageNum=1000，pageSize=10），本质是要获取「第 9991~10000 条」数据。

2.核心问题

传统分页用 LIMIT offset, size 实现，但 offset 越大，性能越差，原因是：
MySQL 执行 LIMIT 9990, 10 时，会先扫描出前 9990 条数据并丢弃，只返回最后 10 条

3.解决方案

1.基于「游标 / 上一页最后一条数据」分页

  • 核心思路：放弃「页码」，改用「上一页最后一条数据的唯一标识（如 ID）」作为查询条件，避免 offset 扫描无效数据。

  • 优势：

    • 无论翻多少页，SQL 只扫描需要的 10 条数据，性能稳定
    • 适合「下拉加载更多」的场景（APP / 网页常见）

  • 局限：

    • 无法直接跳转到指定页码（比如用户想直接点第 1000 页）

    • 依赖有序的唯一标识（如自增 ID、时间戳 + ID）

2.产品层面禁止访问过深的页码

  • 只允许查询前 x 页，
  • 强制用户通过筛选条件（如时间、分类）缩小数据范围，再分页

3.缓存 / 预计算（高并发场景）

  • 对热门数据（如前 100 页）做缓存（Redis），深分页数据预计算后存入缓存，避免直接查数据库

五、主从延时

主从延时本质上是从库复制、执行主库 binlog 的速度跟不上主库产生 binlog 的速度，背后涉及主库、网络、从库等多方面因素

  1. 主库层面的原因

主库写入压力过大：如果主库短时间内有大量 DML 操作（INSERT/UPDATE/DELETE）、大事务（比如一次性更新 100 万行数据），会产生大量 binlog，从库处理速度根本跟不上。

  1. 网络层面的原因

网络带宽 / 延迟问题：主库的 binlog 通过网络传输到从库的 IO 线程，如果主从节点跨机房、跨地域部署，网络延迟（比如 RTT>100ms）、带宽不足（比如大量大事务的 binlog 传输占满带宽），会直接导致从库获取 binlog 的速度变慢。

  1. 从库层面的核心原因

从库硬件性能不足：从库的 CPU、内存、磁盘 IO（比如用机械硬盘代替 SSD）配置远低于主库，执行 SQL 的速度慢。比如主库是 16 核 32G+SSD，从库是 4 核 8G+HDD，即使没有并发问题，单条 SQL 执行也会慢。
从库自身负载过高：很多场景下会把从库同时作为查询库，大量业务查询占用从库的 CPU、IO 资源，导致 SQL 线程执行复制的资源被抢占，复制速度下降。
从库锁冲突：从库执行复制的 SQL 时，遇到表锁、行锁（比如从库有慢查询占用锁），会阻塞复制进程，产生延时
